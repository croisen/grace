Document purpose:
Explain the existing Flutter interface, its structure,
navigation, state management, Rust integration, and the work

This document is intended for developers working on Grace.

IMPORTANT:
The Flutter UI is an existing implementation, not a mockup.

The current interface is a frontend prototype. Some controls
already work, some are connected to Rust, and others are
placeholders awaiting application functionality.

============================================================
1. PROJECT OVERVIEW
============================================================

Grace is a programming-language syntax drill application.

The current project uses:

- Flutter for its user interface.
- Dart for frontend logic.
- Rust for backend functionality.
- Flutter Rust Bridge (FRB) for communication between Dart
  and Rust.

The current application entry point is:

    lib/main.dart

It initializes the Rust library and launches GraceApp.

The new UI lives in:

    lib/ui/

The previous prototype screen still exists in:

    lib/screens/drill_screen.dart

However, the current main.dart launches GraceApp, not the
previous MyApp/DrillScreen interface.

Please use lib/ui/ as the current frontend foundation.

3. APPLICATION ENTRY POINT
============================================================

FILE:

    lib/main.dart

Current responsibilities:

1. Initialize Flutter bindings.
2. Initialize the generated Rust bridge.
3. Launch GraceApp.

Current implementation:

    Future<void> main() async {
      WidgetsFlutterBinding.ensureInitialized();
      await RustLib.init();
      runApp(const GraceApp());
    }

Do not remove RustLib.init() without replacing it with
another appropriate initialization mechanism.

GraceApp is the root of the new UI.

FILE:

Responsibilities:

- Creates MaterialApp.

------------------------------------------------------------
8.1 RUST GENERATOR INTEGRATION
------------------------------------------------------------

The screen already imports the generated Dart bindings for
the Rust drill generators.

Current generator calls:

    generateVariable(...)
    generateIfStatement()
    generateElseIf()
    generateMatchStatement()
    generateWhileStatement()
    generateForStatement()
    generateLoopStatement()
    generateFunction()

These are already integrated.

The screen randomly selects one of the selected concepts
and invokes the corresponding generator.

For most concept generators, the returned object contains:

    conditions
    answer

The variable generator is different:

    conditions
    code

The screen correctly uses r.code for variable drills.

The conditions are displayed to the student.

The expected answer is stored internally in the screen
state. It should not be displayed before submission.

IMPORTANT:

Do not unnecessarily replace the existing generator calls.

They already work through the generated Flutter Rust Bridge
bindings in the captured project.

If the backend changes a generator's signature or return
structure, regenerate the FRB bindings and update the
corresponding Dart integration.

The variable generator currently uses:

    choice = 1

This means integer variables (i32) are selected.

The mutability argument is randomized between 0 and 1.

The current UI does not expose String variable selection.

------------------------------------------------------------
8.2 CONDITIONS OVERLAY
------------------------------------------------------------

The conditions overlay displays the exercise instructions.

It can be dismissed by:

- Tapping the editor background.
- Pressing the close icon.

The floating action button toggles the overlay.

Relevant methods:

    _toggleConditions()
    _dismissConditions()

Preserve this behavior when modifying the screen.

8.3 TERMINAL EDITOR
------------------------------------------------------------

The screen uses:

    TerminalEditor

The editor receives:

    controller
    dark
    palette

The controller belongs to DrillCardScreen, not the editor.

The editor currently provides:

- Full-screen terminal appearance.
- Line numbers.
- Monospaced text.
- Multiline text input.
- Light and dark terminal appearances.
- Different terminal palettes.

The editor is located at:

    lib/ui/widgets/terminal_editor.dart

Currently it is a Flutter TextField-based editor.

It does not yet provide a complete programming IDE.

There is no implemented:

- Syntax highlighting.
- Autocomplete.
- Code compilation.
- Rust compiler diagnostics.
- Parser integration.

These can be considered future improvements.

Please do not unnecessarily replace the editor merely

------------------------------------------------------------
8.4 SUBMIT BUTTON
------------------------------------------------------------

CURRENT IMPLEMENTATION:

    void _onSubmit() {
      ScaffoldMessenger.of(context).showSnackBar(
        const SnackBar(
          content: Text('Submitted (checker not implemented yet)')
        ),
      );

      Future.delayed(
        const Duration(milliseconds: 500),
        _goToNext
      );
    }

This is a placeholder.

It does not inspect the student's code.

It does not compare the submitted answer with the expected
answer.

It automatically advances after submission.

REQUIRED INTEGRATION:

Replace the placeholder with an actual submission flow.

Conceptually:

    final source = _codeController.text;

    // Send source to the answer-checking backend.
    // Receive evaluation result.
    // Display feedback.
    // Decide whether to retry or advance.

The exact backend API is not implemented by this UI.

Coordinate with the backend developer about the expected
function signature and result structure.

The UI should eventually be able to display:

- Correct answer.
- Incorrect answer.
- Syntax errors.
- Useful feedback.
- Retry or continue options.

Do not expose expectedAnswer to the student as part of
normal exercise presentation.

------------------------------------------------------------
8.5 SKIP AND SESSION COMPLETION
------------------------------------------------------------

The skip button calls:

    _onSkip()

Which invokes:

    _goToNext()

The current session uses:

    currentIndex
    totalCards

When the last card is completed or skipped, the screen
displays a session completion dialog.

The dialog currently returns the user to the first route.

When implementing progress tracking, make sure skipping
and successful completion are recorded differently.

The Rust source lives under:

    rust/src/

The bridge configuration is:

    flutter_rust_bridge.yaml

The bridge is initialized in main.dart:

    await RustLib.init();

The frontend should call public Rust functions through
the generated Dart bindings.

Do not manually edit generated FRB files.

When the public Rust API changes, regenerate the bindings
using the project's Flutter Rust Bridge configuration
and verify that both sides agree.

Existing generated drill bindings should be preserved.

The existing UI can be connected to application logic
without putting everything directly inside individual
screen widgets.

One possible organization is:

    lib/
    |
    |-- ui/
    |   |-- screens/
    |   |-- widgets/
    |
    |-- models/
    |   |-- deck.dart

    |   |-- deck_service.dart
    |   |-- drill_service.dart
    |   |-- settings_service.dart
    |
    |-- rust/
        |-- generated FRB bindings

This is a suggestion, not a mandatory restructuring.

The current screen structure is already usable.

Possible responsibilities:

DECK SERVICE:
- Create decks.
- Retrieve decks.
- Update decks.
- Delete decks.
- Store and retrieve progress.

DRILL SERVICE:
- Request randomized exercises.
- Manage exercise sessions.
- Submit source code for checking.
- Receive evaluation results.

SETTINGS SERVICE:
- Save appearance settings.
- Restore settings when Grace starts.

MODELS:
- Provide structured data instead of passing loosely
  typed Maps throughout the application.

Please choose an implementation appropriate to the existing
project rather than introducing unnecessary abstractions.

15. SUGGESTED IMPLEMENTATION ORDER
============================================================

A practical order for integrating functionality:

1. Keep the current UI and navigation.
2. Define the deck data model.
3. Connect deck creation and storage.
4. Populate DeckListScreen from stored data.
5. Implement opening existing decks.
6. Connect actual answer submission.
7. Display evaluation feedback.
8. Record session results and progress.
9. Persist user settings.
10. Add search and other convenience features.

The frontend and backend developers should coordinate
on function signatures and data structures.

Avoid changing the UI's visual structure unless a real
technical or usability requirement justifies the change.
